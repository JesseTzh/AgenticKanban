# 技术架构

## 概览

AgenticKanban 采用前后端分离的单仓库结构：生产部署时，Go 服务提供 JSON API 并托管已构建的 React 单页应用；GitHub Pages 则仅部署启用 demo 模式的静态前端。

```text
浏览器
  |
  +-- 生产环境 --> Go / Gin --> 内存缓存 --> SQLite
  |                     |
  |                     +--> 静态前端产物（web/dist）
  |
  +-- GitHub Pages --> Vite 静态产物 --> 内置 demo 数据
```

## 仓库结构

| 路径 | 职责 |
| --- | --- |
| `cmd/server` | 服务启动、依赖组装、优雅停机 |
| `internal/httpapi` | Gin 路由、认证中间件、请求处理与静态文件回退 |
| `internal/store` | 业务数据访问、任务流转、审计记录 |
| `internal/domain` | 核心领域模型和工作流常量 |
| `internal/auth` | 密码验证、会话与 Token 哈希 |
| `internal/permission` | 基于角色的权限校验 |
| `internal/db` | SQLite 连接与顺序迁移执行 |
| `migrations` | 数据库 Schema 迁移 |
| `web` | React + TypeScript + Vite 前端 |
| `.github/workflows` | GitHub Pages 构建与部署工作流 |

## 服务端

服务端使用 Go 和 Gin。`cmd/server` 在启动时加载环境配置，打开 SQLite、执行迁移、确保初始管理员存在，并创建缓存和权限执行器，最后将这些依赖注入 HTTP 路由。

### API 与静态资源

所有业务接口位于 `/api`，响应统一为以下结构：

```json
{
  "data": {},
  "error": null
}
```

未匹配到 API 的 `GET`/`HEAD` 请求优先返回已存在的静态文件，否则回退至 `web/dist/index.html`，因此生产环境支持前端 history 路由刷新和直达链接。

接口按调用方分为三类：

| 调用方 | 入口 | 认证方式 | 主要职责 |
| --- | --- | --- | --- |
| 浏览器用户 | `/api/*` | `ak_session` HttpOnly Cookie | 项目、任务、仓库、测试、密钥管理 |
| 外部仓库 | `/api/webhooks/:repoID/:secret` | URL Secret 与签名校验 | 同步 Webhook 事件和 Commit |
| Agent | `/api/agent/*` | `Authorization: Bearer <agent-key>` | 领取任务并提交拆解、开发和代码审核结果 |

### 认证与授权

用户名密码验证成功后，服务创建随机会话 Token，只在客户端保存为 `ak_session` Cookie；服务端和缓存均使用 Token 哈希作为会话标识。会话缓存 TTL 为 5 分钟，缓存未命中时从 SQLite 查询。

浏览器业务接口通过会话中间件识别用户，再由权限执行器按角色、资源和动作授权。Agent API 使用与用户会话独立的 Agent Key，数据库只保存其哈希。密码与 Token 的散列都带有服务端 Secret，生产环境必须通过环境变量配置这些 Secret。

### 领域与任务流转

`internal/store` 是数据访问与工作流写入边界。任务变更会写入 `task_histories`，关键业务动作写入 `audit_logs`；Agent 处理、人工审核、代码关联和测试验收保留独立记录。

任务主要在以下阶段间流转：

```text
需求澄清 -> 技术拆解 -> 代码审核 -> 测试验收 -> 完成
                 ^             |
                 +-------------+
                   审核或测试退回
```

任务状态、Agent 可执行标记与阶段转换由 Store 层集中校验，避免单个 HTTP handler 绕过工作流规则。

## 数据层

数据持久化使用 SQLite（`modernc.org/sqlite`），连接启用外键、WAL 模式和 busy timeout，并限制为单连接。迁移文件按文件名排序执行，已执行版本记录在 `schema_migrations`。

核心数据分为：

- 身份与权限：`users`、`sessions`、`agent_tokens`
- 项目与任务：`projects`、`boards`、`board_stages`、`tasks`、`task_refs`
- 交付过程：`agent_runs`、`approvals`、`reviews`、`test_records`、`task_histories`
- 仓库集成：`repositories`、`webhook_events`、`commits`、`task_commits`
- 审计：`audit_logs`

项目、任务和仓库通过软删除字段保留历史；相关引用关系使用外键约束维护完整性。

## 前端

前端位于 `web`，使用 React、TypeScript、Vite、React Router、TanStack Query、Tailwind CSS 与 shadcn/ui 组件。

```text
main.tsx
  -> AppProviders（主题、QueryClient、BrowserRouter）
  -> App（路由）
  -> 功能页（登录、项目、看板、仓库交付、Agent 密钥）
  -> lib/api（统一请求、响应解包、401 跳转）
```

React Router 负责页面路由，TanStack Query 管理远程数据查询与写入后的缓存失效。`lib/api` 统一附加 Cookie 凭据、解析 API 信封，并在受保护请求收到 `401` 时回到登录页。构建时通过 `VITE_BASE_PATH` 设置路由 basename 和静态资源前缀，以适配 GitHub Pages 的仓库子路径。

## GitHub Pages Demo

工作流 `.github/workflows/deploy-pages.yml` 在 `main` 推送或手动触发时执行：安装锁定依赖、以 `VITE_DEMO_MODE=true` 构建、生成 `404.html` 作为 SPA 回退，并使用 GitHub Pages Actions 发布。

demo 模式由 `VITE_DEMO_MODE` 控制，具有以下行为：

- 根路径默认显示登录页，任意用户名和密码均可进入演示项目。
- `lib/demo-data.ts` 提供项目、任务、仓库、Commit、Agent 记录和密钥的内置只读数据。
- `lib/api.ts` 拦截 API 调用并返回内置数据；写入调用返回空成功响应，不发送网络请求、不持久化。
- `VITE_BASE_PATH` 来自 `actions/configure-pages`，使资源和浏览器路由在 `/AgenticKanban/` 等子路径下正常工作。

因此 GitHub Pages 演示站不包含 Go 服务、数据库、真实账号或任何生产凭据。

## 配置与可观测性

服务端通过环境变量配置运行环境、监听地址、SQLite 路径、会话 TTL、Secret、Webhook 基础地址、前端产物目录和日志级别，完整清单见 `configs/config.example.env`。

服务使用 `slog` 输出 JSON 日志，并在每个 HTTP 请求结束时记录方法、路由、状态码和耗时。`/api/health` 可用于健康检查。
